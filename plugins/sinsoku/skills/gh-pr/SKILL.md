# gh-pr スキル

## 手順

### ステップ1: 現状把握

最初に比較対象を決める。以下を `<base>` として後続のコマンドに使う:

```bash
base="origin/$(gh repo view --json defaultBranchRef -q .defaultBranchRef.name)"
```

**ローカルの `main` / `master` を `<base>` に使ってはならない。** fetch していないと古く、他人の変更が diff とコミット一覧に混入する。必ず `origin/` 付きのリモート追跡ブランチを使う。

`gh` が使えないリモート（GitHub 以外）では `git symbolic-ref --short refs/remotes/origin/HEAD` で代替する。

続いて以下を**並列**で実行:

- `git log <base>..HEAD --oneline`（ブランチのコミット一覧）
- `git diff <base>...HEAD --stat`（変更ファイルの全体像）
- `gh pr view --json url,title,body`（既存 PR の有無。あれば編集モード、なければ作成モード）
- `git status -sb`（push 済みか、未コミットの変更がないか）
- PR テンプレートの確認: `.github/pull_request_template.md`（あれば構成はテンプレートに従う。チェックリストは正直に埋め、未実施の項目を `[x]` にしない）
- 言語判定: 既存 PR やコミットログに合わせる（git-commit スキルと同じ基準）

### ステップ1.5: 分割判定（1 PR 1 変更）

diff に独立した複数の変更（特にリファクタリングと機能変更の混在）があれば、分割を提案する。最終判断はユーザーに委ねる。

### ステップ2: タイトルと本文の生成

#### タイトル

- コミットメッセージ1行目と同じ基準（簡潔な要約・命令形・50文字以内推奨）
- squash マージ運用では PR タイトルがコミット1行目になるため、prefix の要否・型は git-commit スキルの判定ルール（chore を既定とし条件を満たしたときだけ昇格）をそのまま適用する

#### 本文の基本原則

PR は提案である。説明文の役割は課題への共感を得ること、解決策への納得は diff と動作確認が担う。この分担があるため、diff から読み取れる WHAT を本文に書かず、説明文は why に集中させる。長く詳細な説明はレビュワーの認知負荷を上げ、要点が埋もれる。

説明の量は変更のリスク・非自明性に比例させる。自明な変更（typo・lint 修正等）は1〜2文で完結してよく、テンプレートを機械的に埋めない。非自明な変更では説明を惜しまない。

構成（テンプレートがあればそれを優先）:

- **動機・背景**: 誰がどんな場面で困るか（ユースケース）を先頭に書き、レビュワーが課題に共感できるようにする。主張より検証可能な事実（エラー出力・再現例）で示す。関連 Issue があれば `Fixes #N` をここに置く
- **変更内容**: 採用した方式を要約。diff から読み取れる WHAT は書かない。却下案はレビューを楽にする場合のみ根拠付きで書く
- **動作確認**: マージ前に確認できる項目のみ。CI が包含する項目は個別に並べず「CI が成功すること」に集約する。手元で確認した項目は実行したコマンドと結果を書き、レビュワーが再現できる形にする。実測値・改善結果は変更内容ではなくここに書く。コードリーディングで確認した項目は、読んだファイル名やメソッド名ではなく、確認できた結論と対象のバージョンを書く（実装レベルのメソッド名は「書いてはならないもの」に該当する）

**非自明な判断は必ず書く。** 意図的な挙動変更、あえて対応しなかったこととその理由、スコープ外の残作業は、diff からレビュワーが気づけないため先回りして開示する。「自明な WHAT を書かない」の裏面となるルール。

#### 変更種別ごとの定型

- **バグ修正**: 最小再現コードと実際のエラー出力を示し、根本原因を説明する。原因を導入したコミット/PR を `git log -S` や blame で特定できたら参照する。影響を受ける条件（構成・経路）が限定的ならそれも書く
- **性能改善**: before/after を表形式で示し、測定環境・条件を注記する
- **挙動変更**: 旧挙動と新挙動を対比する。過去の設計を覆す場合は「当時は正しかった判断の前提が、何によって変わったか」を書く。旧挙動が必要な人向けの移行パスがあれば示す
- **一時しのぎ（バージョン固定・revert 等）**: 恒久対応の Issue/PR を参照し、暫定対応であることを明示する
- **UI に見える変更**: スクリーンショットや録画を添付する（before/after）

#### 記述ルール

- 結論を先に置き、一文を長くしない。専門用語の連続を避ける
- 略語は初出で正式名称を括弧書き。プロジェクト固有ツールは冒頭で一言説明する
- 変更が多ファイルに渡る場合は、読み始めるファイルと順序を示す
- 変更が既存コードの前例や過去の設計判断に沿う場合はそれを明示する（「X と同じパターン」）。レビュワーの検証コストが下がる
- 影響を受けないケースとその理由を1〜2文で書く（壊れないことの証明）
- テストを追加した場合、それが何の回帰を防ぐかを一言書く。修正前にテストだけ適用して失敗する（RED→GREEN）ことを示せるとなお良い
- CHANGELOG の追記規約があるリポジトリでは要否を判定する（例: 挙動変更は書く、軽微な修正やドキュメントは書かない）
- PR で変更していない既存ファイルへリンクする場合、`/blob/main/...` ではなく `/blob/<sha>/...` を使う。SHA は `origin/main` の HEAD（main 直リンクはファイル移動・削除でリンク切れになる）
- 将来予定（「別 Issue で扱う」「次回対応」）は Issue ID が確定している場合のみ書く。それ以外は「本 PR では対応しない」のような現状の判断に留める

#### 書いてはならないもの

- 根拠のない「見てほしい点」「レビューで注意してほしい点」セクション。実装に具体的な不安がある場合のみ、その理由とセットで書く
- 「〜したい。」で終わる文（チームに共有する文書として不自然）
- ネガティブ・悲観的な表現（「意味がない」「無駄」等）。既存コードやその作者を貶める言い回しは、同じ事実を中立的な表現に置き換える
- 調査過程の副産物（原因切り分けのログ、同じ主張への追加の証拠リンク、実装レベルのメソッド名）。マージ可否の判断を変えない情報は書かない

### ステップ3: 提示前の読み返し

ユーザーに見せる前に本文を一度読み返し、各文へ以下を自問して該当する文を削る:

1. 「diff を読めば分かるか？」→ Yes なら削除
2. 「この文はレビュワーのマージ判断を変えるか？」→ No なら削除
3. 「実際に出る疑問への回答か、想定反論への予防線か」→ 予防線なら削除

3 は 1 と 2 を通過した文を落とすためにある。diff から読み取れず判断にも関係するが、誰も抱かない疑問に答えている文がこれに当たる。典型例:

- 標準的な手法・ライブラリを選んだ理由
- 採用しなかった代替案（レビュワーが実際に提案しそうな場合を除く）
- チームが既に知っている前提への注記

最後に本文の分量を diff の規模と見比べる。数行の diff に説明が数段落あるなら 2 と 3 を適用しきれていない。

初稿をそのまま見せない。冗長さは生成直後より読み返したときに気づきやすい。

### ステップ4: ユーザー確認（1回のみ）

以下をまとめて1回だけ提示し、承認を待つ。**承認前に `gh pr create` / `gh pr edit` を実行しない。**

- タイトル
- 本文の全文
- base ブランチ
- push が未実施の場合はその旨（承認後に `git push -u origin <branch>` を実行する）
- 編集モードの場合は変更前後の差分

### ステップ5: 実行

承認後に順次実行:

1. 未 push なら `git push -u origin <ブランチ名>`
2. 作成または編集（本文は HEREDOC で渡す）:

```bash
gh pr create --title "タイトル" --body "$(cat <<'EOF'
本文
EOF
)"
```

編集モードでは `gh pr edit` に同じ形式で `--title` / `--body` を渡す。

レビュー中に変更内容が説明文と食い違ったら、マージ前に説明文を更新する（説明文は将来の開発者が読む永続的な記録のため）。

## 禁止事項

- ユーザー承認前の `gh pr create` / `gh pr edit` / `gh pr comment`
- 「確認して」と依頼された既存 PR を、明示的な指示なく編集すること。編集せず、事実確認と修正案の提示に留める
- `--web` の使用（承認した内容と投稿内容がずれるため）
